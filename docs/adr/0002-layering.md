# 0002 分层和依赖规则

- 状态：已采纳
- 日期：2026-10-02

## 背景

- 一套代码要跑在 Web、微信、抖音三个环境里。逻辑代码只要碰了某个环境独有的东西（`window`、`wx`、`tt`，或者某个平台不支持的 Canvas API），换个平台就会坏，而且常常要到真机上才发现。
- 开发主要由 AI 分多次会话完成，每次会话都可能顺手走捷径。规则只写在文档里不够，必须能被机器检查。
- 用户明确要求要有机制，防止架构在开发过程中跑偏。

## 决定

1. 代码分成 core、engine、game、platform、entry 五层。引用方向见 [architecture.md](../architecture.md#分层)。
2. 平台能力只通过 `platform/types.ts` 里的 Platform 接口提供。entry 创建平台实例并交给游戏；core、engine、game 不认识具体平台。
3. 画图只通过 Canvas2D 子集接口。这个接口只包含微信、抖音、浏览器都支持的方法。
4. 规则由三道检查执行，都汇总在 `npm run check` 里：
   - **分层 tsconfig**：业务层编译时不带浏览器和微信的类型库。
   - **`tools/check-arch.mjs`**：检查引用方向、全局对象、npm 包、文件位置。
   - **假平台 `test/fake-platform.ts`**：game 层的测试跑在 node 里的假平台上。
5. 0.3 实现架构检查时细化了几条规则：
   - 整个 `src` 都不引用 npm 包和 node 内置模块，entry 也一样。
   - 平台实现之间不互相引用，入口之间也不互相引用。
   - `wx`、`tt`、`window` 这些名字在业务层里保留，局部变量也不用。

## 理由

- 分层 tsconfig 能拦住 `window`、`document`，但拦不住 `globalThis`、`declare const wx`，也看不出 core 引用了 game。架构检查补上这些。
- 规则写成代码，违规时报错直接说明违反了哪条、该怎么改，AI 和人都看得懂。
- 业务层只依赖接口，所以能在 node 里用假平台完整测试。平台相关的问题都集中在很薄的平台实现里，真机验证只需要盯这一层。

## 代价

- Platform 接口和 Canvas2D 子集要自己维护。游戏需要新的平台能力时，要先改接口（写 ADR），再给三个平台实现和假平台都补上。
- 平台实现之间不能共用代码，微信和抖音的适配可能有不少重复。
- 不能直接用 npm 上的库，需要的工具函数要自己写。
- 架构检查本身也要维护：加新层、新平台时，要改它的规则和测试。

## 什么时候重新考虑

- 要支持新平台，比如支付宝、快手。
- 微信和抖音的适配代码大量重复，成了负担。这时可以写新 ADR，讨论加一层共享的小游戏适配代码。
- 某个功能确实需要第三方库。
