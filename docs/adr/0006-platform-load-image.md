# 0006 Platform 增加读图：游戏层给路径，平台给回能交给 drawImage 的图

- 状态：已采纳
- 日期：2026-10-03

## 背景

- 5.5 要把物品上的 emoji 换成 AI 生成的图标（规格见 [art-spec.md](../art-spec.md)）。游戏层不能直接用 `Image`、`wx.createImage`、`tt.createImage`（[ADR 0002](0002-layering.md)），Platform 接口里也没有读图的办法。
- Canvas2D 子集里已经有 `drawImage` 和 `ImageSource`（"具体是什么对象由各平台决定，游戏层只会把它交给 drawImage"），所以**只缺"把一个文件读成 ImageSource"**。这不改 Canvas2D 子集。

## 决定

`Platform` 增加一个成员：

```ts
/**
 * 读一张图。path 相对于产物根目录，例如 'assets/icons/boot.png'。
 * 读成功返回 ImageSource；文件不存在、解码失败、平台不支持都返回 null，不会抛异常，也不会一直不返回。
 */
loadImage(path: string): Promise<ImageSource | null>;
```

1. **读失败是正常情况，不是错误。** 游戏层拿到 null 就继续画 emoji，所以图可以一张一张地补，也不会因为某张图坏了就卡住。
2. **游戏层只请求产物里真有的图。** 构建时扫描 `assets/icons/`，把有哪些图作为常量（`__ICON_IDS__`）编译进入口，入口再交给游戏。这样没有图的物品不会发出请求：浏览器对 404 会在控制台报错，开发者工具里也会报，既吵又会让浏览器冒烟测试把"没有图"当成错误。
3. **图是静态资源，放在 `assets/`，构建时原样复制进每个平台的产物**（`dist/<平台>/assets/...`），不打进 JS。包体检查的 300KB 上限只管 JS；图单独有一项素材检查（`npm run check:assets`：文件名对得上物品、PNG、192×192、带透明、每张不超过上限、总量不超过上限）。
4. 三端对应：Web 用 `new Image()`，微信用 `wx.createImage()`，抖音用 `tt.createImage()`（**抖音这端没有对照官方文档**）；都是设 `onload`、`onerror`、`src`。
5. 假平台 `test/fake-platform.ts` 记录读过哪些路径，测试可以决定哪张图读成功、哪张失败，以及什么时候读完。

## 理由

- 只加一个成员，是游戏层读图需要的最小集合。
- 不用图集、不引入打包图片的工具（那要新依赖，CLAUDE.md 规定要先问）：17 张单独的小图，请求都是读本地包，没有网络开销。
- 构建期决定"有哪些图"，运行期不用探测，三个平台的行为一致。

## 代价

- 三个平台实现各有一份几乎一样的读图代码（和 ADR 0005 一样，平台实现之间不能互相引用）。
- 图放进了产物，**小游戏的主包有大小上限**（我记得微信是 4MB，抖音以后台为准）。17 张压缩过的 192×192 图约 0.5～0.7MB，离得远；以后加大图、背景图、音频时要重新看。
- 抖音的 `createImage` 没验证，不存在时所有图读失败，游戏退回 emoji，不会崩。

## 什么时候重新考虑

- 图多了（背景、箱子、动画帧）：换成图集，到时看要不要引入工具。
- 需要分包或网络下载图片。
