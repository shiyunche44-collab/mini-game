# 路线图

分阶段的任务和进度。下一个任务就是表里第一个没打 ✅ 的任务。工作方式见 [CLAUDE.md](../CLAUDE.md#工作方式)。

每做完一个任务，在同一次提交里把它标成 ✅。阶段结束后由用户决定是否合并到 `main`。

备注：

- 1.1：草稿里的 `weightedOrder` 用了 `Math.pow`，已按 ADR 0003 换成逐个按权重抽取的写法（分布相同）。`test/core-determinism.test.ts` 检查 core 里没有 `Math.pow`、`**`、`Math.random`、`Date` 这类写法。
- 1.2：已按 ADR 0003 加上前 200 关的指纹测试。生成器改动让某一关变样时，要同时加 `GENERATOR_VERSION`、更新指纹。单次搜索的步数预算从草稿的 4000 降到 300：草稿的最坏一关要 40～60ms，现在 2 万关里最慢约 17ms，每次尝试成功率在 80% 以上。
- 1.4：`Level` 新增 `rotate`（这关能不能旋转），一局的规则要用；不影响生成结果，指纹没变。提示按答案摆：已经摆对的不挪，形状相同的物品互换，先摆大件，用托盘里的物品，挡路的退回托盘；不能旋转的关卡里只用朝向本来就对的物品。`restore` 对存档逐项检查，要么整份恢复，要么不改动。"重来"保留朝向和提示次数。
- 1.5：存档里记下进行中的关卡是哪个 `GENERATOR_VERSION` 生成的，对不上就让这一关重新开始（ADR 0003）。
- 1.5 做完的样子：`Progress` 是纯数据（版本、当前关卡、进行中的局面、上次插屏时间），`loadProgress` 对 storage 里读出来的任何东西都不抛错，能留的进度尽量留（损坏就从第 1 关开始；局面不对只丢这一局；版本比现在新就只留关卡号）。读写 `platform.storage` 由 game 层做，key 是 `SAVE_KEY`。core 里没有时钟，插屏频控的函数由调用方传 `now`。插屏规则：通关第 5、8、11…… 关后弹，离上次不足 90 秒不弹（这个 90 秒是我定的，没有别处依据，可以改 `INTERSTITIAL_MIN_GAP_MS`）。`drafts/` 已删除。

## 阶段 3：可玩原型（Web）

| 编号 | 任务 | 验收标准 | 状态 |
|---|---|---|---|
| 3.1 | 拖动放置：吸附预览、放不下退回托盘、手指拖动时物品抬高 | 假平台测试：把一件物品拖进箱子 | ✅ |
| 3.2 | 点按旋转（托盘里和箱子里都能转）+ 动画 | 假平台测试 | ✅ |
| 3.3 | 过关：合盖、盖章、登机牌、下一站、存档 | 假平台测试：自动通关第 1 关 | ✅ |
| 3.4 | 提示、跳关、重来 + 模拟激励视频 | 假平台测试：看完广告才给提示，提前关闭不给 | ✅ |
| 3.5 | Playwright 冒烟测试 + 发布手机试玩链接 | **玩法门禁**：用户试玩前 10 关。好玩再进入阶段 4，不好玩先调玩法 ✅ |

备注：

- 3.1：拖动的逻辑都在 `game/PlayScene.ts`，吸附的计算是纯函数 `game/snap.ts`。规则：手指按在物品上（托盘里按物品的正方形位置，箱子里按格子）拖动，物品放大到箱子里的大小、抬高；拖到放得下的位置时画半透明预览；松手落进去，放不下就飞回去。从箱子里拿起的，松手在托盘上是退回托盘，其他放不下的情况回到原来的位置。拖动期间 `Game` 的状态不动，松手才改，所以被系统打断什么都不会丢。
- 3.1：物品比手指高出 0.7 格（`LIFT_CELLS`），吸附半径 0.8 格（`SNAP_RADIUS`），放大 / 落位 / 退回的时长是 110 / 130 / 240 毫秒。这些数字都是我定的，没有别处依据，3.5 试玩时看手感再调。吸附按"拿起完成之后的大小和高度"算，不按动画中间的值，所以手很快时结果也一样。
- 3.1：假平台修了一个浮点问题：时间不对齐帧点时，`advance(FRAME_MS)` 可能漏掉一帧。`FakeCanvas2D` 的调用记录里也加了 `shadowBlur`，用来测拿起时的影子。
- 3.2：点中物品（托盘里按它的正方形位置，箱子里按格子）调 `Game.rotate`。转得动：把转好之后的物品倒转 90° 画出来再转回 0，约 190ms，末尾略过冲；连点时接着当前角度继续转。箱子里周围没空位转不开：物品左右抖一下（约 300ms，幅度 0.12 格，越抖越小）。这一关不能旋转、或者物品怎么转形状都一样（2×2 的书、单格的袜子）时点了没有任何反馈。这几个数字和"不能转的不给反馈"都是我定的，3.5 试玩时看是否需要提示玩家。
- 3.2：抖动的波形在 `engine/tween.ts` 的 `wave`，用折线代替 sin。测试辅助抽到了 `test/play-helpers.ts`，3.1、3.2 的测试共用。
- 3.3：流程在 `game/Session.ts`：读存档、玩当前这一关、过关、下一站，并把触摸交给当前场景或过关画面。`PlayScene` 只发"局面变了"和"全部装下了"两个事件，不碰存档和广告。存档：每次摆放、取出、旋转之后存进行中的局面；全部装下的那一刻就存"下一关"，不等玩家点"下一站"，所以在登机牌上退出也不会白玩（代价是这一次的插屏广告会跳过）。存档损坏、版本不对、局面对不上都不会崩，规则见 `core/progress.ts`。
- 3.3：过关画面在 `game/WinOverlay.ts`：先等最后一件物品落稳（220ms），箱盖从上面合下来（420ms），印章压下去（260ms），最后暗幕加登机牌升起（420ms），共约 1.6 秒。登机牌出来之前点一下屏幕直接跳到最后，不会进下一关；出来之后点"下一站"才进。登机牌上写：出发地（这一关）、到达地（下一关）、行李件数、提示次数、登机口（由关卡号算出的装饰）和条形码（同样由关卡号算，不用随机数）。
- 3.3：点"下一站"时按 `shouldShowInterstitial` 判断弹不弹插屏（通关第 5、8、11…… 关，且离上次不足 90 秒不弹），放完才进下一关，记下的是放完的时间；广告期间不响应触摸。重来、提示、跳关三个按钮现在还是摆设，3.4 做。
- 3.3：调试参数 `?level=N` 现在不读也不写存档（进度只在这次打开里有效）；`&hints=99` 把箱子摆满，直接进入过关画面，用来看结算。
- 3.3：下一关直接切换，没有转场动画。这是我没做的，记在 backlog。
- 3.4：按钮的逻辑在 `game/Session.ts`，`PlayScene` 只发"点了哪个按钮"的事件，并提供 `restart()` 和 `applyHint()` 两个动作。重来免费：箱子里的物品飞回托盘，朝向和提示次数保留，箱子本来就是空的就不存档。提示和跳关先 `rewarded(...)`，返回 true 才给；返回 false（中途关闭、加载失败）什么都不给，也不存档。看广告期间 `busy`：不响应任何触摸，重复点按钮只请求一次广告。跳关后不弹插屏（设计文档规定），也不出现过关画面。提示摆好的物品从原位飞到答案位置（220ms），被挤开的飞回托盘；提示先摆最大的（规则在 `Game.hint`）。
- 3.4：Web 的模拟激励视频是 DOM 弹层（`platform/web.ts`）：暗幕加卡片，倒计时 3 秒（`MOCK_AD_SECONDS`，我定的，真广告通常 15～30 秒）后才能点"领取奖励"，右上角 ✕ 随时可以关（返回 false）。同一时间只有一个广告，已经有一个在播时再请求直接返回 false。弹层是 DOM，node 里测不了，3.4 用 Playwright 手动验证了一遍（提前关闭、等倒计时领取、重来、跳关、存档），3.5 会把它做成自动的冒烟测试。插屏广告 Web 上还是只打日志。
- 4.2 提醒（已按这个做，见 4.2 的备注）：微信、抖音没有 DOM，Web 这个弹层不能直接用，没填广告位 id 时改用 `wx.showModal` / `tt.showModal` 的确认框。
- 3.5 已就绪的部分：`npm run smoke`（`tools/smoke.mjs`）在 Chromium 里把 Web 版玩一遍：页面能打开、手机触摸和鼠标拖动、刷新后接着玩、提示和跳关的模拟广告（提前关闭不给）、通关第 1 关出现登机牌、转屏刷新。它需要浏览器，所以不在 `npm run check` 里，CI 里单独一个 `smoke` 任务跑。发布：`.github/workflows/pages.yml` + `tools/publish-pages.mjs`，每次推送 `dev` 先过 `npm run check`，再把产物推到 `gh-pages` 分支。详细步骤、要看什么、怎么反馈见 [playtest.md](playtest.md)。
- 3.5 为手机试玩做的两处 Web 改动：`platform/web.ts` 读真实的安全区（`env(safe-area-inset-*)`），不然 iPhone 上行李牌会被刘海盖住；`entry/web.ts` 在宽度变化（转屏）时刷新页面，高度变化（地址栏收起）不刷新。安全区在真机上才能验证，自动测试测不到。
- 3.5 玩法门禁已过：用户在手机上试玩前 10 关，结论是好玩，进入阶段 4。试玩中提出的具体问题没有记录（用户只给了"好玩"的结论）；手感参数（吸附半径、抬高、动画时长）和前 10 关的难度梯度仍按 backlog 里的记录，以后有反馈再调。


## 阶段 4：微信和抖音同时适配

| 编号 | 任务 | 验收标准 | 状态 |
|---|---|---|---|
| 4.1 | 两端基础适配（画布、触摸、存储、前后台）+ 两端构建和项目模板 | 产物里没有浏览器接口；用户在两个开发者工具里导入后能玩 | ✅ |
| 4.2 | 激励视频和插屏（两端）；没填广告位 id 时退回模拟广告 | 用户在开发者工具里走通广告流程 | ✅ |
| 4.3 | 分享（两端）+ 抖音录屏分享 | 真机验证 | ✅ |
| 4.4 | 抖音侧边栏复访 + 两端埋点 | 真机验证 | ✅ |

备注：

- 4.1 已就绪的部分：`platform/wechat.ts`、`platform/douyin.ts` 把 `wx` / `tt` 翻译成 Platform 接口（画布、触摸、存储、前后台、安全区、震动）；`npm run build:wechat`、`npm run build:douyin` 产出可以直接导入开发者工具的目录（`game.js`、`game.json`、`project.config.json`，模板在 `platforms/`）；两个入口的 tsconfig 不带 DOM，所以平台实现里写 `window` 会在编译期报错（backlog 里原来那一条已经解决）。"产物里没有浏览器接口"的验收是自动的：`tools/mini-bundle.test.mjs` 把真正构建出的产物放进只有 `wx`（或 `tt`）的 node 沙箱里运行，碰到 `window`、`document` 就会 ReferenceError；沙箱里还会点击、拖动、读坏存档。
- 4.1 的设计：`wx` / `tt` 和 `requestAnimationFrame` 由入口传进平台实现，不在平台实现里直接取全局，所以假对象就能测（`test/mini-platform.test.ts`，两个平台跑同一组测试）。画布先设成物理像素，再按它最后实际的大小算缩放，平台不听设置时也不会画歪。安全区把平台给的坐标范围换算成四边各让开多远。存储存的是 JSON 字符串，没存过（空字符串、undefined）、坏了都回默认值。
- 4.1 抖音这一端没有类型库（不加依赖）：`platform/tt.d.ts` 里 `tt` 是 `any`，`douyin.ts` 自己声明了用到的接口，**签名没有对照过官方文档**，只能靠你在抖音开发者工具里验证（步骤见 [devtools.md](devtools.md)）。微信这一端入口里传的是真的 `wx`，类型检查会对照微信的类型库。
- 4.1 做完时占位的部分：广告、分享、埋点。广告在 4.2、分享在 4.3 已经做了，埋点在 4.4。两个 `project.config.json` 里的 appid 是占位，导入时填你自己的。
- 4.1 已验收：用户在微信、抖音开发者工具里导入后试玩，结论是没问题。具体机型和细节没有记录。
- 4.2 已就绪的部分：`platform/wechat.ts`、`douyin.ts` 的 `ads` 有两种工作方式，由入口里的 `AD_UNITS`（`src/entry/wechat.ts`、`douyin.ts`，现在都是空字符串）决定。**填了广告位 id**：激励视频用平台的全局单例，只监听一次关闭 / 出错事件，靠"正在放的那一次"区分结果；`isEnded` 为 true 才给，老版本关闭时不带参数也当作看完；第一次 `show` 失败（还没加载好）就 `load` 一次再放，再失败返回 false；同一时间只放一个，已经有一个在放时直接返回 false。插屏每次新建一个实例，放完（关闭、出错、`show` 被拒绝）就销毁并返回。**没填 id**：激励视频弹系统确认框（"模拟广告（广告位还没开通）"），点"领取奖励"才给，点"关闭"、点框外、弹不出来都不给；插屏直接跳过。任何路径都不抛异常。
- 4.2 的取舍：确认框没有倒计时，不像 Web 的弹层要等 3 秒才能领，因为 `showModal` 不能动态改按钮；所以开发者工具里走"没填 id"的流程时，规则（点了才给、可以关）和 Web 一样，但没有等待感。真广告的等待和关闭按钮是平台自己的界面，游戏画布在广告期间不变（backlog 里"按钮按下没有视觉反馈"那一条提到了"加载中"状态）。
- 4.2 做完时没有验证的部分（真广告至今没验证过）：真的激励视频和插屏。没有广告位 id，开发者工具里的广告也只是模拟。`createRewardedVideoAd`、`createInterstitialAd` 的调用方式微信这端对照了类型库（入口类型检查会拦签名写错），抖音这端和 4.1 一样是照微信的写法推的，没有对照官方文档。拿到广告位 id 之后要在真机上走一遍：看完给奖励、中途关闭不给、连着看两次、断网时点提示。
- 4.2 已验收：用户走通了没填广告位 id 时的确认框流程，结论是没问题。真广告（填了广告位 id）还没验证过，拿到广告位 id 之后要在真机上再走一遍。
- 4.3 已就绪的部分：登机牌上"下一站"的上面多了一排描边按钮（`game/WinOverlay.ts`）：**分享给朋友**（两端都有，Web 上只打日志），平台支持录屏（现在只有抖音）时旁边再有一个**分享录屏**。分享的标题写通关的关卡号，链接参数是 `from=share&level=N`（现在没人读它，见 backlog）。登机牌出来之前点不到；分享可以重复点，不影响进下一关；录屏分享失败（没录到、玩家取消）什么都不发生，登机牌还在。登机牌从 352 加高到 404 像素，375×667、320×568 上截图确认排得下。
- 4.3 平台这边：两端启动时打开右上角菜单的"转发"，默认标题是"整理行李箱：把行李都装进箱子，就能出发"（`DEFAULT_SHARE_TITLE`，我定的）；老版本没有这些接口时静默跳过。抖音的录屏（`platform/douyin.ts` 的 `createRecorder`）是个小状态机：空闲、录制中、正在停止。游戏每一关开头 `start`、通关时 `stop`，玩家连点"下一站"时新一关的 `start` 会赶在上一段 `onStop` 之前到，所以"正在停止"时来的 `start` 要等停完再开始；分享时如果还在收尾就等它。单段最长 300 秒（`RECORD_SECONDS`，平台上限），录满自己停下也走同一条路。跳关或者重来不会中断录制，所以一段视频里可能带着前一关的内容（记在 backlog）。
- 4.3 做完时没有验证的部分（用户事后验收时说没问题，下面这些没有逐条确认）：**全部都没有在真机上验证**，这正是 4.3 的验收标准。抖音的 `getGameRecorderManager`、`onStop` 的 `videoPath`、`shareAppMessage({channel: 'video', extra: {videoPath}})` 这几个接口的写法是凭印象写的，没有对照官方文档，抖音这端没有类型库；微信的 `shareAppMessage`、`showShareMenu`、`onShareAppMessage` 对照了类型库，但分享面板长什么样、对方点开后进的是哪一关（我们还不读链接参数，永远进玩家自己的进度）、录屏对低端机卡不卡，只有真机知道。
- 4.3 已验收：用户真机验证分享和抖音录屏分享，结论是没问题。具体机型和细节没有记录。
- 4.4 范围（用户选的）：只做侧边栏入口和埋点，**不改 Platform 接口**。不做的：启动场景和分享链接参数的读取（所以统计不到玩家从哪进来）、侧边栏复访奖励。这两样记在 backlog，要做先写 ADR。
- 4.4 已就绪的部分：事件表见 [analytics.md](analytics.md)，一共 10 个事件，集中在 `game/Session.ts` 的 `EVENTS`。微信走 `wx.reportEvent`，抖音走 `tt.reportAnalytics`，布尔值在平台实现里转 1 / 0，上报失败不影响游戏。抖音的 `sidebar`（`platform/douyin.ts` 的 `createSidebar`）用 `tt.checkScene` 问入口是否存在、`tt.navigateToScene` 打开引导页，任何失败都当作不可用。`Session` 启动时问一次，答案回来之前登机牌不画这个按钮；平台说不可用就永远不画。
- 4.4 登机牌的变化：分享这一排现在最多三个按钮（分享、录屏、侧边栏），三个时换成短的字（"分享""录屏""侧边栏"）；320×568、375×667 截图确认排得下。
- 4.4 做完时没有验证的部分（用户事后验收时说没问题，下面这些没有逐条确认）：`tt.checkScene` / `tt.navigateToScene` 的参数和返回值（`scene: 'sidebar'`、`res.isExist`）是凭印象写的，没有对照官方文档，抖音这端没有类型库；`isExist` 是否真的表示"这个客户端能放侧边栏入口"也只能真机确认。微信的 `reportEvent` 对照了类型库，但后台没配置的事件收不到，字段个数和长度的限制我没有查。
- 4.4 已验收：用户真机验证抖音侧边栏和埋点，结论是没问题。后台事件配置是否生效、各平台对事件数量和字段长度的限制，没有听到反馈，不确定有没有查过。

## 阶段 5：打磨和上线准备

做的顺序：先做不依赖外部素材的手感、难度、引导，再做要改接口或要素材的音效、美术，最后做资质提审。

| 编号 | 任务 | 验收标准 | 状态 |
|---|---|---|---|
| 5.1 | 手感打磨：按钮按下反馈、提示物品高亮、下一关转场动画 | 假平台测试；浏览器截图确认 | ✅ |
| 5.2 | 难度曲线：前几关指定新物品第一次出现在哪一关；降低 1×2 小件的权重；加 `GENERATOR_VERSION`、更新指纹 | `npm run levels:preview` 前 30 关，用户判断梯度；`npm run check` 通过 | |
| 5.3 | 新手引导：前 3 关的操作提示（拖、点按旋转） | 假平台测试 + 截图 | |
| 5.4 | 音效：要在 Platform 加音频接口，**先写 ADR 并经用户同意** | 两端开发者工具里能听到 | |
| 5.5 | 美术换图：`pieceView.ts` 换成图集，包体仍不超过 300KB | 截图确认 | |
| 5.6 | 资质和提审：隐私协议、防沉迷、提审材料清单（以文档为主） | 材料清单用户确认 | |

备注：

- 5.5 的素材由谁提供、什么来源（自己画、买、AI 生成）还没定，会影响做法和提审时的版权说明，开工前要问用户。
- 上线后再做"护照"收集、每日挑战、排行榜。
- 5.1：三项都在 `game/` 里，不动 Platform 接口和分层。**按钮反馈**：点中重来、提示、跳关时按钮缩到 92%（`PRESS_SCALE`）再弹回，影子变浅，一共 160ms。这是"点下去"的反馈，不是"手指按着"的状态：后者要给 `GestureHandlers` 加按下事件，这次没做。**提示高亮**：提示摆好的物品飞到位之后，身上闪两下黄光再暗下去，约 900ms（`GLOW_MS`）；拿起、旋转、重来都会让光立刻消失；光是半透明的，不盖住物品上的 emoji。**换关转场**：新的一关从右边滑进来，旧的一关连同登机牌向左滑出去，300ms（`SLIDE_MS`），跳关也一样；滑动期间不响应触摸，存档在滑动开始时就已经是新的一关。滑动距离取整到物理像素，不然两个画面交界处会有一条细缝。
- 5.1 这些数字（回弹 92% / 160ms、闪光 900ms、滑动 300ms）都是我定的，没有别处依据，真机上看手感再调。滑动期间 300ms 不能操作，如果玩家觉得"卡"，可以改成允许提前操作。
- 5.1 的测试：`test/game-feedback.test.ts`。现有的两处测试（连续跳关、连续通关）在换关之后要先等滑完才能点，已加上 `advance(SLIDE_MS)`；冒烟测试里提示领取之后要等光暗下去再采样书的颜色，等待从 500ms 改成 1500ms。
